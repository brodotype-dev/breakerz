UX changes from deferred speed-audit work

Two of last night's deferred follow-ups are user-visible. The rest (PostHog audit, service worker tuning, DB indexes, bundle reduction, PreReleaseLayout split) are invisible perf wins. This mock shows the visible two side-by-side so you can decide if either is worth prioritizing.

1. Break page server-component conversion + Suspense streaming

Today the whole page is a 893-line client component — server returns HTML shell, then the browser sequentially fetches product → pricing → observations → chase cards → market-delta. User sees a "Loading break…" screen for the whole wait.

Time to first paint

~800ms→~200ms
Server returns rendered HTML for nav + product header + format-mix form immediately. Today the entire page waits on a client-side useEffect.

Time to interactive (form usable)

~2500ms→~200ms
Format counters + team picker + ask-price field can be touched before pricing data finishes streaming in. Today the whole page is locked until every fetch resolves.

Total time to fully rendered

~2500ms→~1800ms
Slight improvement from server-rendering the static parts in parallel, but the big win is perceived performance — user sees content flowing in rather than staring at a spinner.

Scope

893-line refactor
Real work. Need to split state-owning client-only pieces (analysis form, drawer, team chip picker) from data-fetching server pieces. ~2 sessions, needs thorough testing on every consumer surface.
UX honest take: the perceived speed win is real and large. The Time-to-Interactive drop from 2.5s → 200ms is the difference between "I'm waiting for the app" and "the app is responsive." But this is a real refactor — not a one-evening change. Worth doing when consumer-perf is the next priority focus.

2. Player drawer FMV caching

Today every drawer open fires /api/player-comps → CardHedger FMV batch (60 items) → 1-3s wait. Proposed: cache by (playerProductId, grade), 10-min TTL. Same-session re-opens hit cache.
/break/2026-bowman-baseball — drawer Today
0ms
/break/2026-bowman-baseball — drawer Proposed (cache hit)
0ms

Drawer-open feel (cache hit)

1.5–3s→~50ms
If the user already opened this player in the last 10 min, prices are already in cache. No CH call. Drawer feels instant.

Drawer-open feel (cache miss)

1.5–3s→1.5–3s
First open for a player is the same speed (we still have to fetch FMV). The win is on every subsequent open in the session, which is common when comparing players.

Refresh affordance (stale cache)

subtle "Refreshing…" chip
If the cache is stale (>10 min) we render the cached number immediately and revalidate in background. Small inline indicator so user knows it's still warming up.

Scope

~3 hours
Single-file change in app/api/player-comps/route.ts — wrap getCardFmvBatch in unstable_cache keyed by (card_id, grade). Tested pattern (same one we used for /api/pricing last night).
UX honest take: small change, real win — the "compare two players side by side" flow (open A, close, open B, close, re-open A) goes from 4 × ~2s waits to 1 × ~2s + 3 × instant. Most users won't notice in a single drawer open, but will feel the difference when they're shopping through a roster. Cheap; recommend doing before the bigger break-page refactor.
